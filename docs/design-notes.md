此仓库不罗列功能，只记录我在开发过程中遇到的设计取舍和问题。

缓存击穿问题，缓存穿透问题，二级缓存，缓存一致性，滑动窗口限流，秒杀库存扣减，异步下单，超时关单，支付回调，其他 Redis 特性

1. 热点 Key 失效（缓存击穿）

对于平台中商铺的信息其实是一个变动比较少的、读多写少的数据，因此比较适合写入 Redis 缓存中，降低数据库的压力。

当一个热点 Key（比如秒杀活动详情）TTL 过期的瞬间，几千个请求同时涌入。如果直接查数据库重建缓存，数据库瞬间就会崩掉。这就是缓存击穿。我调研了两种主流方案：

互斥锁方案：当缓存失效时，让所有请求去抢锁，抢到锁的那一个线程去查数据库重建缓存，其他线程休眠等待。
逻辑过期方案：不给 Redis Key 设置物理 TTL，而是把过期时间存在 Value 里。线程取出数据后判断是否过期。如果过期了，获取互斥锁，开启一个独立 goroutine 去后台更新缓存，自己直接返回旧数据。

方案对比（CAP 定理的抉择）：

互斥锁：保证了一致性，牺牲了可用性。
逻辑过期：保证了可用性，而牺牲了一致性。

商铺详情、热搜榜单这类社交媒体类型的数据，对一致性的要求并不是强一致性，用户看到的热搜榜单晚了 2 秒更新，其实无伤大雅（AP 模型，重可用性）。

最终结论：我为了保证服务的可用性，选择了逻辑过期方案。实现上用一个 RedisData 结构把数据和逻辑过期时间打包进 Value，查询时先判断是否过期，没过期直接返回；过期了抢互斥锁，抢到的开独立 goroutine 异步重建，自己直接返回旧数据，没抢到的也直接返回旧数据。

这里有一个坑：逻辑过期方案要求缓存里必须先有数据，首次查询没有缓存时返回空，秒杀场景下首查就会失败。所以我在启动时做了预热，把全部商铺一次性写入逻辑过期缓存，避免首查失败。

验证环节：单测覆盖了「锁被占时第二个请求拿旧数据返回、loader 零调用」这个场景；全链路冒烟也验证了重建后新数据可见。

2. 查询不存在的数据（缓存穿透）

如果有人恶意用脚本疯狂请求不存在的商铺 ID，请求就会直接穿透 Redis 打到数据库。我了解到两种解决方案：

缓存空值：实现简单，虽然存在额外内存占用，但可以通过设置较短时间的 TTL 解决。
布隆过滤器：存在误判可能性，且实现复杂，需要引入新的组件，需要维护。

因为目前平台的商铺数量并不是很大，我选择了缓存空值的方案：查询未命中时回源查库，查无结果就写入空值缓存（TTL 2 分钟）。顺带解决雪崩问题：缓存 TTL 加了随机偏移，避免大面积同时失效。

3. 搭建二级缓存架构（ristretto + Redis）

秒杀优惠券详情页是更新频率极低、访问频率很高的数据，而 Redis 单实例性能有上限，单个热点 Key 的压力过大，Redis 可能成为系统瓶颈。

对于这种极热数据，我引入了 ristretto 作为进程本地缓存。请求进来先查本地内存，没有再查 Redis，最后才查数据库。

这里有个数据一致性的坑：集群部署下，数据库改了，怎么通知所有机器清理本地缓存？引入广播机制又太复杂了。我想通了一个点：既然是秒杀详情页，短暂的不一致是可以容忍的，所以给本地缓存设置了极短的 TTL（5 秒），只靠 TTL 自动刷新，代码简单，效果也足够好。

1. Redis 单实例压力过大，为什么不搭建 Redis 集群？第一是各方面的成本问题。第二即使搭建了 Redis 集群，集群主要是为了解决海量数据存储和整体吞吐量的问题，但它解决不了单热点 Key 的问题。热 Key 存在于某个 Redis 实例上，依然会使得单台 Redis 实例压力过大，除非对该热 Key 进行分片，分散到不同的 Redis 实例上，这样实现复杂度又增加了。所以本地缓存方案相比之下更简单、更直接。

2. 本地缓存和数据库数据的一致性是怎么保证的？可选 MQ 广播清理（所有节点监听并删除本地缓存），但这会让架构变得非常重，增加了维护成本。我选择了 TTL 短过期：业务场景是「秒杀详情页」，用户看到 2 秒前的「旧描述」或「旧库存显示」，对业务影响非常小，不需要复杂的广播机制，仅仅依靠 TTL 过期自动刷新，就能保证数据在 5 秒内最终一致。

3. ristretto 的实现原理是什么？选择 ristretto 是因为它是目前 Go 生态中性能最强的本地缓存，底层算法就是 Caffeine 的 W-TinyLFU 思路：没有使用简单的 LRU，而是把存储数据的 hashmap 分成窗口区、试用区和保护区三个部分，每个区域是一个 LRU 双端队列，大小随着命中率变化自动调节，类似 JVM 的新生代老年代设计。读写操作也做了类似 WAL 的缓冲优化，减少多线程竞争锁的开销。实际使用中我只给了它 1MB 容量，只放极热 key。

4. 删缓存失败怎么办（缓存一致性）

商铺更新采用 Cache Aside 模式：先更新数据库，再删缓存。问题在于删缓存失败怎么办？我比较了几种做法：

不处理：删除失败是低概率事件，但一旦发生缓存就是永久脏数据，直到 TTL 过期。
同步重试：删除失败就重试，会阻塞更新主流程，响应延迟不稳定。
MQ 补偿重试：删除失败把 key 发到 MQ，消费者异步重删，不影响更新接口的响应时间。

最终结论：我选择了 MQ 补偿 + TTL 兜底的组合，三层保险。更新成功后同步删除缓存；删除失败把 key 发到 cache-del topic，消费者异步重删，消费失败由 RocketMQ 的重试机制承担；补偿也失败，还有 TTL 兜底（商铺缓存 30 分钟逻辑过期、本地缓存 5 秒）。

1. 补偿消息重复消费怎么办？删缓存这个操作本身是幂等的，删一个不存在的 key 不会报错，所以这条补偿链路不需要像库存回补那样做幂等占位，重复消费多少次都无害。这也是它比库存回补链路结构更简单的原因。

2. 删除失败为什么要做成 fire-and-forget？更新接口的语义是「更新成功就返回」，缓存一致性是最终一致性问题，不应该让低概率的缓存故障拖慢主流程。补偿链路加上 TTL 兜底之后，脏数据的窗口是有界的，这个取舍是划算的。

5. 滑动窗口限流

我考虑到有几种特殊情况：优惠券秒杀时流量过大，需要限流保证系统的可用性；领取无限制的优惠券时，为了避免恶意刷券，针对用户进行限流；针对爬虫爬取商家信息，针对 IP 进行限流。所以系统需要一个限流组件，来完成这几种特殊情况的限制。

我了解有固定窗口、滑动窗口、漏桶、令牌桶这四种限流算法：

固定窗口：在临界点会有允许两倍流量的临界问题，所以一般是不使用这个算法的。
漏桶算法：核心是请求以固定的速率被处理，不管请求的突发性。缺点是无法处理突发流量，在秒杀时我们希望系统在有能力的情况下尽可能处理更多请求，漏桶会导致资源无法充分利用。
令牌桶算法：允许一定程度的突发流量。但如果桶中积累了令牌，这并不符合优惠券秒杀中的公平性。
滑动窗口：记录每个请求的真实时间戳，不管怎么「攒」，只要任意时间窗口内的请求数超标，就能精准拦截。

令牌桶和滑动窗口的选型，本质上是「防御目标」截然不同。令牌桶关注的是系统可用性与用户体验，控制的是全局平均速率，适合允许合理突发的场景。而秒杀优惠券场景关注的是业务公平性与严格风控，主要针对 IP 维度限流，目的是防止黄牛刷单和爬虫抓取，它强制要求请求必须在时间轴上均匀分布，这是对抗爬虫和刷单最有效的手段。所以在风控场景，要的是死板和精准，滑动窗口是最佳选择。

具体到防刷场景，为什么不能容忍突发流量：假设我限制 1 分钟 60 次，黄牛可以休眠 59 秒，攒满 60 个令牌，然后在第 60 秒的一瞬间打出 60 个并发请求。如果是令牌桶，这 60 个请求会全部通过，这对普通用户极不公平。而 Redis ZSet 实现的滑动窗口记录了每一个请求的真实时间戳，不管黑客怎么攒，只要他在任意时间窗口内的请求数超标，我就能精准拦截。虽然 ZSet 的性能（O(logN)）略低于令牌桶，但由于是针对单个用户或 IP 限流，窗口内也就几十个元素，性能损耗完全在可接受范围内。

限流 Lua 脚本：利用 Redis 的 ZSet 数据类型实现。删除超出时间窗口的数据（ZREMRANGEBYSCORE），获取当前窗口内的请求数量（ZCARD），若数量小于限制则添加当前请求，若大于等于则限制本次请求。

为什么要用 Lua 脚本？假如不使用 Lua 脚本，会有并发问题。例如两个用户请求先后执行 Redis 命令 ZCARD，返回当前时间窗口内的请求数均为 99，然后这两个用户请求都认为不应该限流，那么就都放行了，但实际上限制数量是 100，这两个请求应该有一个被拦截下来。所以限流逻辑内的「查看数量」「判断大小」和「添加请求」这几个操作必须连贯，有原子性的要求，所以使用 Lua 脚本。另外使用 Lua 脚本同时也能减少多次网络往返，提升性能。

Go 版的语言差异：Go 没有注解，我把限流做成了 Gin 中间件，限流维度（全局、用户、IP）通过参数注入，注册路由时显式声明窗口大小和请求上限，比如秒杀接口 IP 维度 60 次每分钟、领券接口用户维度 10 次每分钟。另外 Redis 故障时限流直接放行，限流组件不阻塞业务。

6. Redis + Lua 实现高并发库存扣减与一人一单校验

这是整个项目最核心的难点，我经历了三个阶段的优化：

数据库悲观锁：直接 select ... for update。结果很明显，请求串行化，性能极差，数据库连接池瞬间被打满。
数据库乐观锁（CAS）：update ... where stock > 0。虽然解决了超卖，但数据库依然扛不住高并发读写，且「一人一单」逻辑在集群下失效（进程内锁锁不住其他实例）。
Redis + Lua + MQ 异步架构（最终方案）：利用 Lua 脚本的原子性，在 Redis 内存中完成「库存判断」和「一人一单校验」。校验通过后，发送消息到 RocketMQ，立即给前端返回「排队中」。后端消费者慢慢消费消息，写入 MySQL。收益：将同步的 DB 操作转为毫秒级的 Redis 操作。

设计考量：第一，不想让 MySQL 数据库去承载高并发的下单资格判断，可以在 Redis 中完成用户下单资格的判断。第二，既然使用了 Redis，那么我联想到 Lua 正好是原子性的，可以解决一人一单的并发安全问题，也就不再需要使用分布式锁，方便了很多。

优惠券库存信息：使用 String 即可，key：业务前缀+优惠券的ID，value：库存数量。
订单信息：使用 Set 数据类型即可，key：业务前缀+优惠券的ID，value：所有购买过该优惠券的用户 ID。

这样，就做到了一人一单。此时下单资格的判断（即达到库存不超卖、一人一单）就完全不需要涉及 MySQL 数据库，都是在 Redis 中完成，因为 Redis 是基于内存的，因此大大提高了秒杀业务的性能。Lua 的返回码：0 成功、1 库存不足、2 重复下单、-1 无库存 key（秒杀未预热）。

验证环节：我用 testcontainers 起了真 MySQL、Redis 和 RocketMQ 跑集成测试，验证并发秒杀不超卖；压测用 hey 打 5000 个请求、100 并发，验证成功响应数等于库存数、异步落库的行数等于库存数、对账任务日志无 mismatch。

7. 引入 RocketMQ 将同步下单流程优化为异步消息处理

在秒杀这个高并发的场景下，扣减库存、生成订单，其实是两次 MySQL 数据库操作，使得整个秒杀业务的性能受到很大影响。

这其实是一个同步流程：判断资格 -> 扣减库存 -> 生成订单。但是其实在判断完用户有资格下单（库存不超卖、一人一单）后，就意味着用户下单成功、秒杀成功。至于 MySQL 的库存扣减和订单生成，完全可以异步的来做。

我们可以在判断用户有下单资格后，发送一个 RocketMQ 消息，另外启动一个消费者监听消息，在消费者的逻辑内去扣减库存、生成订单。通过同步变异步，提高秒杀场景的并发性能。

1. 如果重复消费消息，会不会对业务有所影响？我非常清楚 RocketMQ 保证的是 At Least Once，在网络波动时，重复投递是不可避免的。所以我在业务层（Consumer 端）通过实现幂等性来解决重复消费的问题。这里在确定用户符合下单资格后就会生成一个唯一的订单 ID（高 32 位时间戳 + 低 32 位 Redis 按日自增序列），而发送的 RocketMQ 消息中是携带着这个唯一的订单 ID 的，那么消费者接收消息后，就会去创建订单，也就是写入一条数据库记录，而如果是重复消费的话，那么第二次及后续的消费都会写入数据库记录失败，因为订单 ID 是主键唯一的，如果是因为订单 ID 重复而导致创建订单失败，证明是重复消费，那么后续的流程也就不用再走了，所以即使重复消费消息也不会对业务有影响，保证了业务的幂等性。

2. Redis 库存扣减了，但是数据库的库存没有扣减、订单没有生成怎么办？首先这场秒杀的一个核心要求：一人一单和库存不超卖，是由 Redis 存储库存和订单信息，使用 Lua 完成用户下单资格判断来保证的。所以秒杀的核心要求其实是不受影响的。其次呢，如果消息丢失了，其实只是 MySQL 中的库存信息不正确、以及用户的订单记录没有及时生成。也是数据一致性的问题。所以这是一个最终一致性保障的问题。此时完全可以设计一个兜底策略：设置一个定时任务（每 5 分钟）去检查 Redis 的库存信息和 MySQL 的库存信息是否一致，检查订单是否都正常生成。如果有异常情况，即可修复。其实就是一个对账的思想/策略。可以进一步想：对账时 Redis 里的已购用户集合如果换成 Hash 存「用户 ID -> 订单 ID」的映射，比对的信息会更全，能直接定位是哪一笔订单丢了。目前实现里对账比对的是 Redis 库存/订单数与 MySQL 库存/订单数，不一致就打错误日志，人工介入排查。

3. 如果用户支付后订单记录还没生成怎么办？用户支付本身不依赖于数据库的订单记录。我们后台生成唯一订单 ID 后，调用第三方接口生成支付凭证给前端。当用户支付成功回调回来时，如果我们发现数据库中订单已经被超时关单抢了先（见第 9 节），我们不会强行改状态，而是走退款流程。

工程上还有一个坑：rocketmq-client-go 的 PushConsumer 必须显式 Start()，而且启动时要求 topic 的路由已经存在。消费组启动可能早于 topic 创建，所以 docker-compose 里加了 rocketmq-init 服务预创建 topic，客户端侧再做一个 60 秒的轮询重试启动。

背景说明：Java 版 README 宣称用 RocketMQ、代码实际用 RabbitMQ；Go 移植统一按 README 落地 RocketMQ，两个 topic：seckill-order（异步建单）、stock-refund（库存回补）。

8. 未支付订单到期自动关闭

在优惠券下单后，用户如果超过一定时间内仍未支付，需要关闭订单并释放库存。

我调研了常见的几种方案：

方案一：定时任务（每分钟扫描 MySQL 取出未支付且超时的订单）。优点：实现简单，稳健。缺点：数据量大时对数据库有压力（但只要加好联合索引，效率也很快）。
方案二：RocketMQ 延迟消息。缺点：存在大量无效调度（大部分订单其实已经支付了），RocketMQ 延迟等级固定（1s/5s/10s/30s/1m/2m…），分钟级关单不灵活，且极端情况下可能丢消息，订单就永远关不掉。
方案三：Redis 过期监听。缺点：Redis 的过期策略是惰性删除，不保证实时性，过期通知可能晚几分钟，不可靠。

综合考虑：鉴于单体项目订单量不太大，我使用了方案一（robfig/cron 定时任务，每分钟）。定时扫描还有个延迟队列没有的属性：每轮重查一次，天然不怕丢消息。

1. 会不会存在重复关闭订单，重复增加库存？不会。执行 SQL 时带上条件 update orders set status = '取消' where id = ? and status = '未支付'。只有更新成功（影响行数 > 0）才会去释放库存，乐观锁保证只有一个执行者成功。

2. 如果订单状态设置为关闭，但是库存增加失败怎么办？引入消息队列异步增加库存，若消费者内增加库存失败，则消息队列的机制重试补偿，多次重试依然失败则触发告警，人工介入排查。消费者端用 SETNX 做幂等占位，占位成功才回补，回补失败释放占位等待重试。

这里踩过一个很隐蔽的坑：MySQL 容器没设时区时，CURRENT_TIMESTAMP 存的是 UTC 时间，应用连接串按东八区解析，新订单的创建时间被看成 8 小时前，一启动就被关单任务秒关。表面现象是「订单秒被关闭」，根因是时区错位，最后给 MySQL 容器设了 TZ=Asia/Shanghai 解决。

9. 使用乐观锁解决订单支付和关单的并发问题

如果一笔订单在「超时取消」的那一刻，「用户刚好付款」了，怎么办？

此时后台对于「支付成功的处理」以及「超时关单的处理」，这两者应当是一个成功，一个失败。

数据库乐观锁：
超时关单：update orders set status = '取消' where id = ? and status = '未支付'
支付成功：update orders set status = '已支付' where id = ? and status = '未支付'

这两个 SQL 中的 where 条件都加了 status = '未支付'，利用数据库行锁的特性，这能保证只有一个执行成功，另外一个一定失败。

如果「超时关单」处理成功，「支付成功的回调」处理失败怎么办？这种情况意味着用户已经支付了钱，但是订单被系统超时关闭了。这时候如果发现订单被关闭了，系统需要自动触发原路退回的流程，把钱给用户退回。不能强制改成「已支付」，因为关单通常伴随着释放库存，强行改状态会导致超卖。实现上支付回调发现订单已关闭时返回特定错误码，提示退款流程已触发；重复回调幂等成功。

10. 其他 Redis 特性应用

点赞排行榜（Redis ZSet）：需求是按时间排序的点赞列表。实现：ZADD key score(时间戳) value(userId)。
共同关注（Redis Set）：需求是 A 关注的人和 B 关注的人取交集。实现：SINTER keyA keyB。
附近商户（Redis GEO）：需求是搜索方圆 5km 内的店，按距离排序。实现：底层是 GeoHash 算法，用 GEOSEARCH 按半径取 ID 再回查详情。
用户签到（Redis BitMap）：需求是记录用户一年的签到，极其节省空间。实现：1 个 bit 代表一天。SETBIT/BITFIELD。
UV 统计（HyperLogLog）：需求是统计网站即使百万级访问量，误差允许极小。实现：概率算法，占用内存极小（12KB）。命令：PFADD, PFCOUNT。

这里也有一个测试基础设施的坑：miniredis 不支持 BITFIELD 命令，签到统计的测试只能放在 integration 里，用 testcontainers 起真 Redis 来跑。
